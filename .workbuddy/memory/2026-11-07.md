## 修复：播放时没有总时长、进度条不动

- 根因（两层）：
  1. 客户端 `streamUrl()` 默认对所有歌都带 `format=mp3&maxBitRate=192` 强制转码。转码流是 `200 + Transfer-Encoding: chunked + Accept-Ranges: none`，AVPlayer/ExoPlayer 把它当无限流，`durationStream` 发出 0（darwin `CMTimeGetSeconds` 对不定长流是 NaN → 0）。这个 0 经 `copyWith` 把服务端元数据给的时长**抹掉了** → 总时长 00:00，进度 fraction = 0/0 恒为 0，条不动。
  2. 直传流是 `206 + Content-Length + Accept-Ranges: bytes`，时长、拖动、音质全正常。
- 修复：
  - `Track` 加 `format` 字段，解析 Subsonic `suffix`。
  - `musicfree_client.dart` 新增 `needsTranscode()`：只有 wma/ape/ogg/oga/opus/aifc/ac3/dts/webm 走 mp3 转码，其余直传原始流（顺带解决了 FLAC 全库被压成 192k mp3 的音质问题）。
  - `player.dart` 的 `durationStream` 监听忽略 `<= Duration.zero`，不再让引擎的 0 覆盖元数据时长。
- 实测后端：FLAC 直传 206/audio/flac/22.7MB 完整文件；wma 仍走转码（chunked），此时进度依赖元数据时长（durationStream guard 兜底）。
- 测试 +3（needsTranscode 分类、Track.format），34 全过；DMG/APK 重打包。

## 修复：进度条不动的真正根因（maxBitRate 单独也会触发转码）

- 上轮只把 `format` 置空，但 `streamUrl` 仍带默认 `maxBitRate=192`。实测后端：FLAC 只带 maxBitRate 不带 format 时，响应是 `200 + Transfer-Encoding: chunked + audio/mpeg + Accept-Ranges: none`——**这台 Go 后端仅凭 maxBitRate 就启动转码**，所以直传从未生效，症状原样保留。

- 播放记录（06:0x UTC = 14:0x 本地）显示用户播的「点歌的人」是本地 FLAC，走的仍是 chunked 转码流，与该结论吻合。

## 「Operation Stopped」无法播放定位（2026-11-07 晚，第二轮服务端修复）

## 竖屏卡片一行 3 个
- 首页横向卡片行（热门歌曲/最近播放/专辑/歌单/收藏）原固定 128 宽，竖屏只露 ~2.5 个。新增 `_rowCardWidth(context)`：((屏宽-40-2×gap)/3).clamp(96, 128)，窄屏自动缩到 ~107（一行 3 个），桌面/横屏仍 128。
- 专辑/歌单库网格与艺术家专辑网格：maxCrossAxisExtent 196 → `wide ? 196 : 118`（browse_view 传 wide 参数；detail_view 用 MediaQuery），竖屏 350 可用宽 → 3 列 ~117。

## 一行 3 卡修正：漏算区块卡内边距
- 用户反馈首页卡片行"变化不大"、第三张仍被裁。根因：_rowCardWidth 公式只减屏幕边距 40，漏了 _SectionCard 自身内边距 14×2=28 → 实际可用 322 而需 350，裁 28px。
- 修正：`(width − 68 − gap×2) / 3`，clamp 下限降到 88。iPhone 17 竖屏 390 → 卡片 98px，3 张 + 2 间隙 = 322 恰好铺满。截图验证 3 张完整。
- 教训：算"一行放几个"时要把**所有嵌套容器 padding 逐层相加**，不只是屏幕边距。

## 横屏卡片行铺满（最终方案：LayoutBuilder 实测宽度）
- 用户连续反馈：横屏下热门歌曲/最近播放/专辑/艺术家/收藏行右侧留大片空白（竖屏改 3 卡的钳制 128 让横屏 4 条目只占一半宽度）。
- 中间踩坑：用屏宽推可用宽度两次都错——先漏算 _SectionCard 内边距 28，后漏算横屏 SafeArea 左右各 ~47pt（灵动岛居中导致两侧对称 inset，截图黑融黑看不出来）。
- 最终方案：放弃从屏宽推导，四个行组件（_TrackCardRow/_AlbumRow/_PlaylistRow/_ArtistRow）全部包 LayoutBuilder，用 constraints.maxWidth（行的真实约束宽）算卡宽：n = min(条目数, floor((rowW+gap)/(88+gap)))，卡宽 = (rowW − gap×(n−1))/n，clamp[88,200]。条目少于可容纳数时每张卡放大分摊（横屏 4 条 → ~165px 铺满），多则按最小宽滚动。
- 行高同步自适应：封面行 = 卡宽+48（方形封面+标题块），艺术家行 = 卡宽+36（圆头像 width−8+文字块）；桌面固定 128/92 行高 176/128 恰好等于公式值，行为不变。_ArtistCard 加 width 参数，头像随宽度缩放。
- 教训：**任何"按容器宽算子元素尺寸"的场景直接用 LayoutBuilder 拿约束，不要从 MediaQuery 屏宽反推**——SafeArea、抽屉、rail、嵌套 padding 每层都会吃宽度。

## 鸿蒙旋转不生效

- **现象**：模拟器上旋转（DevEco 模拟器工具栏转屏），caldav-free 会跟着转，MusicFly 不转。两工程 module.json5/build-profile/EntryAbility 逐字节相同、caldav 的 Dart 也没有方向代码，唯一差异是嵌入层请求的方向。
- **根因**：App 从不调用 `SystemChrome.setPreferredOrientations`，鸿蒙窗口方向保持默认 UNSPECIFIED——鸿蒙上 UNSPECIFIED 不跟随传感器/转屏（与 iOS/Android 不同）。caldav-free 应是旧版嵌入层默认请求了自动旋转。
- **修复**：`main()` 里 `SystemChrome.setPreferredOrientations(DeviceOrientation.values)`。ohos 嵌入层把四方向全选（位或 0x0f）映射为 `window.Orientation.AUTO_ROTATION_RESTRICTED`（跟随系统自动旋转开关）；iOS/Android 本就如此，桌面无影响。映射表在 flutter_ohos 的 PlatformChannel.ets decodeOrientations。
- **验证**：新包装上后窗口转储显示 musicfly0 为 2832x1280 横屏，截图横屏布局渲染正常。可用 `hdc shell hidumper -s WindowManagerService -a '-a'` 看 musicfly0 行的宽高确认当前方向。
