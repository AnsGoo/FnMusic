## CI Android 构建失败修复
- 现象：`Dependency 'androidx.lifecycle:lifecycle-process:2.7.0' requires ... compileSdk 34`，`:device_info_plus is currently compiled against android-33`。
- 根因：device_info_plus 9.1.2 的 android/build.gradle 写死 `compileSdkVersion 33`，而 app 自身是 36（flutter.compileSdkVersion=36），只有插件模块拖后腿。
- 修法：`android/build.gradle.kts` 里对 subprojects 加 afterEvaluate，用**反射**把 android 扩展的 compileSdk 抬到 36（`setCompileSdk(Int)` / `compileSdkVersion(Int)` / `setCompileSdkVersion(String)` 三种都试）。不能引用 AGP 类型——根脚本 classpath 不含 AGP。
- **顺序坑**：该块必须放在 `subprojects { project.evaluationDependsOn(":app") }` **之前**，否则报 "Cannot run Project.afterEvaluate when the project is already evaluated"。
- 已验证：`./gradlew -q -I probe.gradle help` 探针输出所有模块（含 device_info_plus）compileSdk=36；`flutter build apk --release` 成功（55MB），target 仍为 36。
- 本机 Windows 上 Kotlin 增量编译报 "Could not close incremental caches ... .tab"，几次复现 → `android/gradle.properties` 固定 `kotlin.incremental=false`（CI 全新工作区无收益损失）。
- 本机 `flutter build appbundle` 会报 "Failed to find cmdline-tools"——本机 Android SDK 没装 cmdline-tools，与仓库无关，CI 上正常。

### 发现并修复：AVSession 未注册（锁屏无媒体面板）

## 修复：鸿蒙端换歌永远播放第一首（vendor just_audio 缓存 bug）（2026-11-09）

- 用户反馈：不管点哪首歌，播的都是 App 启动后第一首播放的热门歌曲。
- 排查：模拟器 + hilog 抓插件日志（vendored 插件加了 MF load/loadAssent/loadUri 调试日志）。铁证：点《不谓侠》时 Dart 侧 setMetadata 已推新歌元数据，但插件 loadAssent/loadUri 加载的还是旧歌 URL（id 未变）。
- 根因：`AudioPlayer.ets getAudioSource()` 按 Dart 侧 audioSource id 缓存 MediaSource。而 Dart 侧 `setAudioSource` 的顶层 `_playlist`（ConcatenatingAudioSource）是播放器常驻单例，id 只生成一次、多次 setUrl 不变 —— 第二次及以后 load 永远命中第一次解码的缓存（旧 children/旧 URL）。子源 uuid 每次是新的，但顶层 id 不变，缓存照样命中。
- 修复：getAudioSource 改为每次按消息重新解码（decodeAudioSource）并刷新 `mediaSources` 缓存（供 setShuffleOrder 按 id 查找）。行为兼容：所有调用点传入的都是全量 JSON 消息。
- 附带加的调试日志保留（MF load/loadAssent/loadUri/AudioPlayer.load/onMethodCall 失败），便于以后排查。
- 实测（模拟器连续三跳）：不谓侠(c256ee1e, 转码流) → 光辉岁月(46a7140a) → J'y Suis(4873df80)，URL 全部正确切换。
- 安装：unsigned HAP 可直接 `hdc install -r` 装进模拟器（无需签名）；hilog 流式抓取必须用 run_in_background 任务（普通子 shell 会中途断）。

## 排查：Android 是否有同样的换歌缓存问题（2026-11-09）

- 结论：**Android/iOS/macOS/Windows 都没有**该 bug，仅 ohos 独有。
- 注意：pubspec.lock 显示 just_audio 实际解析到 path: vendor/just_audio（fork 0.10.5），Android 也在用 vendored fork，其 AudioPlayer.java 同样有按 id 的 mediaSources 缓存 + getAudioSource 逻辑。
- 但 Android 的 `case "load"` 直接取 `audioSourceMap.get("children")` 解码，**跳过了顶层 id 缓存**；子源 id 每次 setUrl 都是新的 uuid → 永远 cache-miss → 全新解码。与官方 0.10.6 逐字节一致。
- ohos 插件的 load 分支是把整个顶层 map 交给 getAudioSource（顶层 playlist id 固定）→ 命中旧缓存 → 只有 ohos 中招（已修）。
- darwin（iOS/macOS）无任何 id 缓存（0 处 mediaSources/getAudioSource）；Windows 走 pub.dev just_audio_windows，无此逻辑。
